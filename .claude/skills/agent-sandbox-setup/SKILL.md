# Agent sandbox setup

Prepare a fresh, automated sandbox so this repo's checks can run, and decide
which extra checks a change needs. This repo ships one agent as several Docker
images (`generic`, `cloudrun`, `lambda`, `azure`, plus the discontinued
`aws_proxied`) that customers
run in their own infrastructure, so a change that breaks an image is far more
costly than a failing unit test.

Treat the steps below as intent, not a script. The source of truth is the
`Dockerfile` and `.circleci/config.yml`; if they disagree with this file,
follow them.

## Ground rules

- Run everything non-interactively. Never wait on a prompt.
- Never pipe a downloaded script into a shell (`curl … | sh`). Install tools
  through a package manager.
- Never claim a check passed if you did not run it. If a check can't run here,
  report it as blocked and say why.

## 1. Python version

Read the versions from the `Dockerfile`, don't hardcode them:

- Most images: the `system-base` stage (`FROM python:<version>-slim`). The
  `requirements*.txt` headers are compiled for the same `major.minor`.
- `azure`: the `azure` stage's base image tag (`python:4-python<version>`). It
  runs a newer Python than the other images.

## 2. System libraries

`pyodbc` needs the unixODBC runtime (`libodbc.so.2`) at import time. Install it
through the OS package manager (Debian/Ubuntu: `libodbc2`, or `unixodbc` on
older releases). Nothing else is needed for the unit tests: the Oracle driver
runs in thin mode, and `teradatasql`, `ibm-db` and `psycopg2-binary` bundle
their native code. `ibm-db` is only installed on x86_64.

## 3. Virtual environment and dependencies

Create the venv at `.venv` in the repo root. Pyright is configured to look
there (`[tool.pyright]` in `pyproject.toml`).

Install every requirements file into it, as CI's `run-linter` job does, plus
`setuptools`:

```bash
uv venv --python <version from step 1> .venv
uv pip install --python .venv setuptools \
  -r requirements.txt -r requirements-dev.txt -r requirements-cloudrun.txt \
  -r requirements-lambda.txt -r requirements-azure.txt
```

`setuptools` isn't in the requirements, and new venvs don't include it. The
git client imports `distutils`, which on Python 3.12+ only exists through the
setuptools shim; without it, the `test_git_*` modules fail to collect.

## 4. Lint and tests

Mirror CI (`run-linter`, `run-test-docker`). The pip `pyright` package needs
Node.js, which CI's lint image ships. In the sandbox, install the `nodejs`
extra at the pinned version:

```bash
uv pip install --python .venv "pyright[nodejs]==<version pinned in requirements-dev.txt>"
.venv/bin/black --check .
.venv/bin/pyright
PYTHONPATH=. .venv/bin/pytest tests
```

## 5. The azure lane

Run this lane when the change touches `requirements.txt`, `requirements-azure*`,
or the `azure` stage. The `azure` image runs on a different Python version, and
CI runs the suite against it separately (`tests-azure`).

Create a second venv with the azure Python version. Install `setuptools`,
`requirements.txt`, `requirements-azure.txt`, `requirements-dev.txt` and
`requirements-cloudrun.txt`, and run `pytest` again. The `tests-azure` Docker
target does the same thing.

If `uv` downloads this interpreter, it has no default CA file
(`ssl.get_default_verify_paths().cafile` is `None`), and the CA bundle tests
fail. Point it at the system bundle:

```bash
SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt PYTHONPATH=. .venv-azure/bin/pytest tests
```

## 6. Changing dependency pins

The `requirements*.txt` files are generated by `pip-compile` from the matching
`.in` files. The command for each file is in its header.

- Use a throwaway venv on the step 1 Python version, with `pip==24.3.1` and
  `pip-tools==7.4.1`. Newer pip releases break this pip-tools version.
- Bump only what you need, with `--upgrade-package <pkg>` (`-P`). A full
  `--upgrade` moves dozens of deliberate pins.
- Files compiled with `-c requirements.txt` must keep that relative path; undo
  any absolute path pip-compile writes into them. Also restore the header
  command line if pip-compile adds flags like `--cert=None` to it.
- The diff against the base branch should only show the pins you meant to change.

## 7. Image checks (only when packaging changes)

Run these when the change touches a `requirements*` file, the `Dockerfile`, or
anything the `Dockerfile` copies into an image (`resources/`). Branch CI builds
only the `tests` and `tests-azure` targets, not the images customers run, so
CI will **not** catch a broken shipped image. This step is the only place that
does before merge.

If Docker isn't available in the sandbox, report this step as blocked, list
the images it would have covered, and say that a person needs to build them.

**Pick the targets.** Build only the images the change can affect:

| Change | Targets |
|---|---|
| `requirements.txt`, or the `system-base` or `base` stage | `generic`, `cloudrun`, `lambda`, `azure` |
| `requirements-cloudrun*` | `cloudrun` |
| `requirements-lambda*`, or the `lambda-builder` or `lambda` stage | `lambda` |
| `requirements-azure*`, or the `azure` stage | `azure` |
| A `resources/` file | every stage that copies it |

Stages inherit from one another (`FROM <stage> AS …`), so a change to a stage
affects every stage built on it.

**Build** each target. Build x86_64 images (`--platform linux/amd64`); that's
what is shipped, and `ibm-db` is only present there.

```bash
docker build --platform linux/amd64 --target <target> -t apollo-check:<target> .
```

Each build needs a few GB of free disk. If a build fails on a package install
with "not enough free space", that's the sandbox, not the change: report it as
blocked.

**Smoke-test** each image: import the agent's entry module and every native
driver, using the image's own interpreter. An import that fails here would
fail in a customer's deployment.

| Target | Interpreter and path |
|---|---|
| `generic`, `cloudrun` | `/app/.venv/bin/python`, working directory `/app` |
| `lambda` | `python3`, working directory `/var/task` |
| `azure` | `python` with `PYTHONPATH=/home/site/wwwroot:/home/site/wwwroot/.python_packages/lib/site-packages` |

```bash
docker run --rm --platform linux/amd64 --entrypoint <interpreter> apollo-check:<target> \
  -c "import oracledb, pyodbc, ibm_db, teradatasql, psycopg2, snowflake.connector; import <entry module>"
```

What to import, per target:

| Target | Entry import | Notes |
|---|---|---|
| `generic` | `apollo.interfaces.generic.main`, `apollo.interfaces.aws.main` | |
| `cloudrun` | `apollo.interfaces.generic.main`, `google.cloud.logging` | `apollo.interfaces.cloudrun.main` needs real GCP credentials at import time |
| `lambda` | `apollo.interfaces.lambda_function.handler` | |
| `azure` | `function_app` (copied to the app root) | Set `APPLICATIONINSIGHTS_CONNECTION_STRING=InstrumentationKey=00000000-0000-0000-0000-000000000000`, since it configures telemetry at import time |

If a path or module above no longer matches the `Dockerfile`, follow the
`Dockerfile` and say so in your report.

`aws_proxied` is discontinued but still built. Its stage only changes the
`CMD` of `generic`, so don't build it; the `generic` row above covers its
entry module.

Also add the package the change bumps to the import list, if it isn't already
covered by one of the imports above.

## Report

Say which of steps 4, 5 and 7 you ran, and the result of each. Step 7 can't
cover paths that only run against a live data source: connection validation,
metadata collection and queries. List the integrations the change could affect
there, so a person can check them on a deployed agent.
